# Week 10 — Continuous Testing & Jenkins CD Validation

## 1. Objective

The primary objective of Week 10 is to integrate, automate, and prove **Continuous Testing** within the existing Jenkins Continuous Deployment (CD) pipeline (`lease-workflow-cd`) for the **Lease Document Approval Workflow** application.

Specifically, this practical verification proves that:
1. **Automated Selenium E2E Tests Execute Under CI**: Selenium WebDriver 4.x browser automation runs headlessly and reliably under the non-interactive Windows service account (`jenkins-svc`).
2. **Failure Propagation**: Maven test failures automatically return non-zero exit codes that fail the Jenkins `Build` stage immediately.
3. **JUnit Test Reporting**: Test result XMLs generated by the Maven Surefire plugin are captured and published to Jenkins via pipeline post-actions (`post { always { junit ... } }`), ensuring visibility of pass/fail metrics on every build.
4. **Deployment Gating**: When a test fails during the `Build` stage, downstream `Package` and `Deploy` stages are strictly skipped, preventing defective binaries from being packaged or deployed to the runtime environment.
5. **Deliberate Regression Detection**: A realistic UI contract regression (breaking a DOM selector expected by an E2E test) is detected by the automated suite in CI.
6. **Safe Restoration**: The defect is corrected and verified without modifying business logic or polluting the mainline integration branch (`develop`).
7. **Clean Pipeline Execution**: A green build passes all unit, service, and Selenium E2E tests, packages the executable Spring Boot JAR, deploys the application to port `8081`, and verifies runtime health via Spring Boot Actuator.

## 2. Existing Pipeline Architecture & Flow

The Continuous Deployment pipeline is declared in `Jenkinsfile` and orchestrated by Jenkins as a multi-stage Declarative Pipeline.

### Successful Deployment Flow

```text
Git Repository (Branch: develop)
       │
       ▼
[Stage 1: Checkout] ──► SCM checkout of target revision using Jenkins credentials
       │
       ▼
[Stage 2: Build] ────► Injects DB credentials, runs 'mvn clean package'
       │               ├─ Unit & Service Tests (JUnit 5)
       │               └─ Headless E2E Tests (Selenium WebDriver + ChromeDriver)
       │
       ▼
[Stage 3: Package] ──► Archives validated target/*.jar artifact & records fingerprints
       │
       ▼
[Stage 4: Deploy] ───► Terminates stale port process, launches background javaw process,
       │               and validates http://localhost:8081/actuator/health
       │
       ▼
[Post: Always] ──────► Publishes Surefire JUnit XML test report to Jenkins Dashboard
```

### Deployment Gating on Test Failure

```text
[Stage 1: Checkout] ──► SCM Checkout (SUCCESS)
       │
       ▼
[Stage 2: Build] ────► 'mvn clean package' executes test suite
       │               └─ Test Assertion / Selenium Element Failure
       │               └─ Maven: BUILD FAILURE (Exit Code 1)
       │
       ▼
[Stage: Build FAILED]
       │
       ├─► [Stage 3: Package] ──► SKIPPED
       ├─► [Stage 4: Deploy] ───► SKIPPED (No process started, port untouched)
       │
       ▼
[Post: Always] ──────► Publishes JUnit Report with Failure Details & Stack Trace
```

## 4. Jenkins Pipeline Parameterization

To allow flexible deployment and test validation across feature and bugfix branches without permanently altering the mainline integration branch (`develop`), the pipeline parameters were configured in both `Jenkinsfile` and `config.xml`:

```groovy
parameters {
  string(name: 'BRANCH_NAME', defaultValue: 'develop', description: 'Branch to build and deploy')
  string(name: 'APP_PORT', defaultValue: '8081', description: 'Port the app will listen on')
  choice(name: 'SPRING_PROFILE', choices: ['dev', 'staging', 'local'], description: 'Active Spring profile')
}
```

### Parameter Rationale:
- **`BRANCH_NAME`**: Enables Jenkins to check out and test isolated feature or regression branches (e.g., `devops/week10-deliberate-selenium-failure`) on demand, while maintaining `develop` as the safe default.
- **`APP_PORT`**: Specifies the target HTTP port (default `8081`) for both deployment and health check validation.
- **`SPRING_PROFILE`**: Determines the active Spring configuration (`dev` by default for CI/CD deployments).

## 5. Continuous Test Reporting Configuration

Test results are published automatically using the Jenkins JUnit plugin. The configuration is declared in the pipeline-level `post` block to guarantee test report collection regardless of build outcome:

```groovy
  post {
    always {
      junit testResults: 'target/surefire-reports/*.xml', allowEmptyResults: true
    }
    success {
      echo "Deployed at http://localhost:${params.APP_PORT} (profile: ${params.SPRING_PROFILE})"
    }
    failure {
      echo "Deploy failed — check console log"
    }
  }
```

### Surefire Integration Details:
- **Test Phase**: All JUnit 5 unit, service, and Selenium E2E tests run in the standard Maven `test` phase executed by `maven-surefire-plugin` (`3.5.6`).
- **Report Location**: XML report files are written to `target/surefire-reports/TEST-*.xml`.
- **Reporting Guarantee**: Because `junit` is placed inside `post { always { ... } }`, Jenkins records pass/fail counts, stack traces, and historical trends even when the `Build` stage fails with exit code 1.

## 7. Deliberate Failure Experiment

To rigorously validate deployment gating and error propagation, a deliberate UI selector regression was introduced into the project.

### Defect Setup:
- **Branch**: `devops/week10-deliberate-selenium-failure`
- **Commit Hash**: `f22e6e5`
- **Commit Message**: `test: deliberately break Selenium selector for Week 10 CI validation`
- **File Modified**: `src/main/resources/templates/submit-request.html`
- **Defect Introduced**: Renamed HTML element selector `#confirmation-request-id` to `#confirmation-request-id-defect`:
  ```html
  <!-- Original -->
  <strong th:text="${requestId}" id="confirmation-request-id" style="color: #ffffff;">#101</strong>

  <!-- Broken -->
  <strong th:text="${requestId}" id="confirmation-request-id-defect" style="color: #ffffff;">#101</strong>
  ```
- **Test Logic**: `SubmitValidLeaseRequestTest.java` was intentionally left unchanged to verify regression detection.

### Expected vs. Actual Behavior:

| Aspect | Expected Behavior | Observed Result | Status |
|---|---|---|---|
| **E2E Test Execution** | `SubmitValidLeaseRequestTest` fails looking for `#confirmation-request-id` | `NoSuchElementException: no such element: Unable to locate element: [id=confirmation-request-id]` | **VERIFIED** |
| **Maven Lifecycle** | Maven terminates with `BUILD FAILURE` | Maven logs `BUILD FAILURE`, Surefire reports 1 error | **VERIFIED** |
| **Jenkins Stage** | `Build` stage fails immediately with non-zero exit | `script returned exit code 1`, Build marked `FAILED` | **VERIFIED** |
| **JUnit Reporting** | Jenkins publishes JUnit test report showing failure | Jenkins displays `Tests (1 failure / +1)` | **VERIFIED** |

## 14. Conclusion

The Week 10 continuous testing practical successfully established a robust **Quality Gate** in the Continuous Deployment pipeline:

1. **Automated Verification**: Every code change pushed to the repository is automatically built and tested against a comprehensive 15-test suite comprising Spring Boot context tests, database service tests, and real-browser Selenium E2E UI tests.
2. **Defect Prevention**: If any test fails, Jenkins immediately fails the build, publishes the exact failure details to the test dashboard, and strictly aborts packaging and deployment.
3. **Continuous Deployment Readiness**: Only changes that pass 100% of automated tests proceed to artifact packaging, process deployment, and automated health verification.
